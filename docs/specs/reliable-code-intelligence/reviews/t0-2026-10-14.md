# T0 harness review

Scope: staged frozen-label harness and authorization fixture only. No raw retrieval results, held-out scores, or future tuning outputs inspected. This is independent fallback adversarial/quality review; specialist models are unavailable. No production changes made.

## Findings

**P1 — Authorization retrieval checks can pass cross-control leaks.** `scripts/dev/code_eval_authorization.py:46` checks only the queried control's `forbidden` list and only rendered text. A private-query response containing `expiredLaunchSequence` passes, as does the reverse. Source-read controls already use all global forbidden sentinels. Apply the global sentinel set to the serialized complete response for every retrieval control as well. Add fake-server failure-path tests for cross-control leakage and leakage in a non-text response field.

**P1 — Duplicate query order can silently omit hard questions.** `scripts/dev/code_eval_corpus.py:76` verifies only ordered-list length. A split with selected IDs `easy, hard` and order `easy, easy` passes validation, runs easy twice, and never runs hard. This can inflate quality and change the predeclared latency distribution without label-hash drift. Reproduced with disposable two-query labels: `load_frozen` accepted IDs `['easy', 'easy']`. Reject duplicate IDs in the global order, and require exact set coverage of the corpus-selected IDs. Test duplicate/substituted order in addition to the existing empty-order test.

**P2 — Corpus containment does not cover runtime output/storage.** `scripts/dev/code_intelligence_eval.py:87-108` accepts output and store paths inside the corpus. Corpus verification happens first; startup opens the DB and writes the JSON report before `scan_repo`. Thus a previously valid frozen corpus gains runtime artifacts between verification and indexing. Reject resolved storage/output paths within corpus root before creating directories or launching the server; also prevent output from overwriting manifest/labels. Add path-containment tests.

**P2 — Post-lock revalidation discards the validated inputs.** `scripts/dev/code_intelligence_eval.py:102` re-reads and validates the manifest/labels/corpus after potentially waiting minutes, but ignores its returned objects. Queries, corpus revision, and baseline-binary expected hash remain from the first load. Replacing the manifest and labels with a different internally valid pair during the wait can yield a run that mixes old queries and new verified bytes. Bind the initial manifest digest and require it unchanged after lock acquisition, or load all inputs and construct/check the report under the lock. Test a manifest/label swap across acquisition without running actual retrieval.

**P2 — Authorization retrieval has no retained-vector positive control.** `adapters/ingest/examples/code_eval_authorization.rs` seeds canonical/graph records only, and the outsider runner never populates vectors or proves those parents existed in a tested projection. Consequently vector authorization could be broken while this battery still passes by having no vector candidate to filter. The owner exact source read is a good canonical-presence control, but does not establish vector coverage. Before using this battery as zero-unauthorized-retrieval evidence, seed leakable projections under an authorized principal, retain them through private/expiry policy transitions, and record projection IDs/presence. Alternatively explicitly classify the current battery as canonical/source+graph coverage and leave retained-vector authorization unverified for the later task. Do not claim this scoped T0 fixture covers a lane it never exercises.
