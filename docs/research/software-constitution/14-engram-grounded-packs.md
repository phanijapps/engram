# 14 — Engram-grounded constitution packs

Date: **2026-11-01**. Status: **analysis and candidate wording, not ratification**.
Scope: the actual checkout: product, architecture, Cargo/pnpm workspaces, runtime seams, constitution registries, gates, CI, launcher and factory. Only this research file changes.

## 1. Judgment: make the packs describe this product, not software in general

Engram is a **contract-first, local-first agentic memory and knowledge engine**. Its customer is an agent/host that must remember across sessions, retrieve grounded context, revise evidence-backed beliefs, and understand code without confusing observations with truth. Rust owns deterministic behavior; generated contracts, N-API/TypeScript and the unified MCP server make that behavior usable by embedders and agents. The installable launcher/agent bundle is also a product surface, not incidental developer tooling (`docs/product/engram.md:15-37`; `README.md:20-31,53-89`; `docs/contracts/constitution/v1/implementation/registry.json:61-80`).

The product has distinct substrates: governed experiential **memory**; source/document/chunk-grounded **knowledge**, including taxonomy/ontology; derived **beliefs** with valid-time semantics; and generation-bound **code intelligence**. Hierarchy compresses retrievable objects; consolidation maintains derived state; retrieval fuses these sources into a bounded, explainable context payload. This is neither a vector database nor an LLM host. The Hono/React demo demonstrates consumption; it does not turn the engine into a hosted application/control-plane product (`docs/product/engram.md:41-143,192-198,241-242`; `docs/architecture/reference.md:16-37`; `core/domain/src/belief.rs:1-5`).

The packs should answer seven different questions: **what Engram promises; where its semantics live; how its artifacts are made; what demonstrates those promises; which checks actually run; what authority/data boundaries cannot be crossed; and what was actually shipped**. Root rails remain the authority. Packs supply Engram-specific applications and counterexamples, not seven copies of RULE-1 through RULE-6.

## 2. Candidate rule format and adoption discipline

Uppercase MUST/MUST NOT/SHOULD carry BCP 14 meaning **if adopted**. Each row has an ID, an Engram-specific statement, typed references to permanent root IDs, and source evidence. Proposed suffixes **101+** avoid reassigning the already-ratified shell IDs; adoption must explicitly retain, supersede or retire old wording, preserving its history.

`refines: PR-005`, for example, means rail 09's root rule—not a similarly named pack rule. `enforced-by:` names an existing check or workflow only where it actually checks/orchestrates the obligation; “partial,” “fixture,” and “manual gap” are intentional limitations, not green badges. Tests cited below were inspected, not claimed executed. `ci/` is reciprocal enforcement metadata, never a new authority over other packs (`docs/constitution/00-INDEX.md:71-93`; `docs/constitution/ci/00-INDEX.md:8-16`).

### 2.1 Product — the highest-value pack

**Belongs here:** the engine's identity, domain distinctions, observable write/recall/forget guarantees, freshness semantics, supported surfaces and honest capability status. Product rules describe an agent's observable outcome; architecture rules below prescribe the implementation seam. Neither the generic OUT-ID requirement nor a feature-count slogan is a substitute.

Useful acceptance questions are concrete: can an agent recall a durable decision in its authorized project next session; does a source revision retire obsolete assertions; does forbidden/redacted content stay absent; does code evidence identify the committed generation actually indexed? These outcomes follow the mission and shipped contracts, not generic “quality” (`docs/product/engram.md:29-47,73-96,127-135`; `core/integration/src/batch.rs:21-30`).

## 3. “Engram as an engine should help build the constitution”

### 3.1 Yes—as an evidence substrate and memory loop, not a legislator

The engine already has the right primitives: a code graph for structure, source/doc chunks for exact evidence, a KG for semantic bridges, governed memory/procedures for decisions and repeated mistakes, beliefs/contradictions for revisable interpretations, and fused recall for bringing those together. The **agent** extracts and proposes; the **owner** decides; deterministic **gates** enforce; Engram stores and retrieves the evidence. This division is explicit in the distill skill: “you do extraction, classification and bridging; server persists/retrieves” (`.agents/skills/engram-distill/SKILL.md:3-18,40-93`).

The engine's current advantage is **connected, revisable evidence**, not natural-language constitutional judgment. A module's frequent dependencies can suggest a boundary; frequency cannot authorize it. A graph missing an edge cannot prove a forbidden dependency absent. A high recall score cannot make a rule normative. A contradiction can request review; it cannot amend a root rail (`core/code/src/lib.rs:3-8`; `core/domain/src/belief.rs:1-5`; `core/knowledge/src/ontology.rs:7-12`).

### 3.2 An implementable authoring loop for this repository

1. **Establish revision and authority first.** Use a host-authorized project/repository binding and read `code_status`; distinguish published OID from observed ref freshness before retrieving architecture evidence. Candidate worktree changes require direct source inspection or a separately authorized scope, not silently rebinding the canonical index. Store the reviewed revision and source hashes with the analysis. This follows the existing binding/status contract (`docs/architecture/domain-data-model.md:61-85`; `core/integration/src/code_binding/status.rs:8-57`).
2. **Collect code and documentary evidence separately.** Rebuild the bound code generation through the provider's registered-locator flow; ingest raw product docs, ADRs, rails, manifests, workflows and registries for verbatim retrieval. Then use `search`, `symbol_context`, `architecture`, `file_dependencies` and `change_impact` where the connected MCP tool profile exposes them. The graph finds candidate locations; `fetch_content`/direct source establishes what they say. Do not assume every MCP tool is a one-shot subcommand (`README.md:82-89`; `.agents/skills/engram-know/SKILL.md:14-22,60-77`; `core/integration/src/code_binding/registration.rs:51-61`).
3. **Make a trace graph, not a bucket of slogans.** Represent a rule's identity and source text, its owning pack, protected capability, real implementation artifacts, gate/test artifacts and decision evidence. Initially use existing classes (`Requirement`, `Behavior`, `Component`, `Configuration`) and declared bridges (`governs`, `describes`, `realized_by`, `extracted_from`). Distill “PR-005 governs recall,” “recall realized_by the inspected composer,” and “this source describes the gate” only after discovering those targets. An `enforced-by` relation in the Markdown catalogue is not automatically a legal ontology predicate (`mcp/engram-mcp/src/ontology.rs:56-113`; `.agents/skills/engram-distill/SKILL.md:42-74`).
4. **Mine rule candidates with counterexamples.** Start with observations: “facts recall calls memory.retrieve”; “SQL exists only in named engine zones”; “bound status separates indexed/observed OIDs.” Ask the agent to propose the smallest BCP-14 obligation, name a violating change and find a negative fixture. For ARC-103 the counterexample is a new lane directly reading memory rows and applying its own RRF. Engram supplies code/doc context; the owner decides whether the observed pattern is intended law, contingent implementation or debt (`core/integration/src/recall.rs:24-30`; `core/integration/src/sqlite/recall.rs:195-219,401-415`).
5. **Verify the enforcement claim outside retrieval.** Read each gate's implementation and workflow invocation, execute its positive/negative fixtures, and record selected paths, features, backends, commands, exit status and omissions. For neutrality, explicitly compare `GATED_PATHS` with the desired boundary; for components, parse Cargo/pnpm inventories and compare both directions. A KG bridge to a gate is evidence of a claimed relationship, not proof that the check blocks the violating change (`tools/ci/check_engine_neutrality.py:27-80`; `tools/ci/check_coherent_integration.py:24-63`; `.github/workflows/ci.yml:28-41,89-98`).
6. **Ratify in Git and the canonical factory journal.** Submit the rule text, counterexample, gate mapping, evidence and compatibility consequences to owner review. Only the approved repository/catalogue amendment changes law. The factory journal remains the decision receipt; indexing it creates a searchable derivative, not a replacement or a self-approved memory event. Factory source/snapshot checks and actual owner instructions remain authoritative (`docs/constitution/00-INDEX.md:69-84`; `.agents/skills/engram-factory/scripts/factory.py:208-244,470-502`).
7. **Distill the accepted revision with source discipline.** Use a stable doc `source_id` and `<doc-id>@<exact-sha>` key; immutable retries retain the payload, later revisions use new keys. Facts enter memory; entities/relationships enter KG; source-bound supersession retires stale assertions and reports counts. Verify bridges and recall after writing. This existing convergence mechanism is useful for constitution maintenance without claiming cross-store ACID (`.agents/skills/engram-distill/SKILL.md:76-93,119-127`; `core/integration/src/batch.rs:9-30`).

**Worked example: repair a false enforcement gap.** Rail 01 still says missing paths are silently skipped (`docs/constitution/01-engine-neutrality.md:31-37`). Current code records a violation and its negative fixture asserts the missing path is named (`tools/ci/check_engine_neutrality.py:65-72`; `tools/ci/tests/test_engine_neutrality.py:11-24`). A drift query should retrieve both, label the rail's gap note stale, and propose a documentation amendment—not weaken EN-004 or claim the entire neutral boundary is proved. The focused two-test run recorded below confirms this narrow fact. This is exactly the kind of connected evidence Engram can make cheap to rediscover.

### 3.3 Maintenance loop: changed code → affected rules → renewed proof

After an approved merge, refresh/rebuild the authorized bound ref and verify the indexed OID, then re-distill changed docs/registries under stable source IDs (`.agents/skills/engram-bound/SKILL.md:58-71`; binding freshness remains the stronger source of truth than a “recently indexed” timestamp). Query affected symbols/files and their `governs`/implementation bridges to prepare a **review queue**, not automatically rewritten law.

Concrete drift classes this queue can expose:
- **Prose ↔ implementation:** retired SurrealDB/two-server/facade claims versus current manifests/provider/MCP code; lexical wiring marked deferred despite an actual lexical lane. Verify both sides before changing a shipped claim (`docs/product/engram.md:106-116,145-153,177-183,215-218`; `core/integration/src/sqlite/recall.rs:249-278`).
- **Rail ↔ gate ↔ workflow:** a gate listed “planned” but executed in CI; a rule that names a script but that script only checks headers; a new root rule without a blocking invocation. This needs parsed registries and workflow/source inspection, not approximate recall alone (`docs/constitution/04-distribution-drift.md:5,21-27`; `tools/ci/check_distribution_drift.py:37-63`; `.github/workflows/ci.yml:32-38`).
- **Source ↔ delivered artifact:** authored skill byte changes, stale wrappers, wrong target/version or an untested repacked launcher. Reuse full-byte parity and packed-artifact verification; source indexing cannot observe arbitrary installed hosts or authenticate npm contents by itself (`packages/launcher/scripts/check-skills-parity.cjs:88-176`; `tools/release/verify-launcher-package.py:58-90`).
- **Decision ↔ current evidence:** a remembered “approved” interpretation whose supporting source changed or whose gate no longer covers the path. Mark it pending review; retain the old event/revision as history. Belief valid-time fields help record interpretation, but record-time replay and automatic constitution-specific invalidation are not delivered guarantees (`core/domain/src/belief.rs:68-95`; `adapters/integration/src/fixtures/belief.rs:74-81`).

Recall can then answer useful questions: “Which approved rule governs this changed lane?”, “Which security promise has only name-level proof?”, “What artifacts did the owner approve for this release?”, and “Which constitution claims are stale at indexed OID X?” Procedures can record the repeatable review/runbook; outcome feedback can say whether recalled guidance actually helped. None of these answers removes the need to inspect the current revision and run the named check (`README.md:64,82-89`; `.agents/skills/engram-know/SKILL.md:60-77`).

### 3.4 Arbitrary repositories and ontology packs: reusable machinery, local law

An arbitrary repository can use the same loop, but must infer its **own** product identity, deployment/distribution surfaces, manifests, authority boundaries and executable proofs. Do not export “Rust core/N-API/pgvector” as universal constitutional rules. A Python service, firmware image or finance application gets different candidate obligations and release evidence; observed engine relationships organize evidence, not justify importing Engram's architecture.

There are two independent meanings of pack:
- A **constitution domain pack** is reviewed normative policy with stable rule IDs and root authority edges.
- An **Engram ontology pack** is runtime vocabulary: the pinned catalogue has 33 standard packs, fetched once with hash verification, converted to classes/properties and sliced into launch config (`core/packs/data/catalogue.json:1-17`; `mcp/engram-mcp/src/pack.rs:1-14`).

For a banking repository, FIBO can give domain terms for “what the governed behavior concerns”; schema.org can do the same for travel. Neither supplies that project's lawful architecture or security policy. Existing DOAP, PROV-O and SKOS entries can help describe project/release, provenance and concept relationships, but there is **no delivered constitution-specific authoring/compiler pack** merely because SHACL/ontology terms exist (`core/packs/data/catalogue.json:111-119,269-280,313-346`; `.agents/skills/engram-domain/SKILL.md:28-76`).

A useful **proposed**, not shipped, vocabulary extension would distinguish `ConstitutionRule`, `DomainPack`, `EnforcementGate`, `EvidenceRun`, `Decision` and explicit `refines`/`enforced_by` relations, with revision-qualified rule/implementation identities. Custom launch JSON can express the vocabulary today, but a validated rule catalogue, authority DAG/cycle checking, rule-to-gate execution and portable export would require separately accepted design/implementation. Register new predicates before distilling them; do not smuggle a new public contract through metadata or assume an OWL/SHACL runtime (`mcp/engram-mcp/src/ontology.rs:22-45,119-122`; `core/knowledge/src/ontology.rs:7-12`; `core/domain/src/rule.rs:1-8,22-26`).

Pack coverage is also not completeness: installation writes full structural records, but agents initially see at most 150 classes/40 predicates. Missing terms require inspecting counts, widening from cache and restarting the server; explicit ontology flags override the conventional generated path. Label collapse/slicing and the converter's supported RDF subset do not implement arbitrary formal reasoning (`core/packs/src/slice.rs:1-23,83-106`; `core/packs/src/converter.rs:1-9,40-46,66-77`; `.agents/skills/engram-domain/SKILL.md:63-105,147-149`; `mcp/engram-mcp/src/ontology.rs:211-236`).

## 4. Recommended adoption order and evidence limits

1. **Ratify product identity and behavioral promises first.** Resolve stale product/golden-path claims against current contracts and recipe capability evidence; adopt the product rules and corresponding architecture seams, not just the existing brief-format shell.
2. **Attach honest enforcement metadata.** Map each candidate to its owner, counterexample, actual command/fixture and blocking/partial/manual status. Reconcile registry paths, component names, gate status and EN-004/L3 notes. CI remains a view; the catalogue must not invent authority edges or coverage.
3. **Close delivery/evidence defects before stronger badges.** Repair retired workflow paths, publish the tested artifacts, establish exact-source security/release linkage, and align evidence stage/actor/hash validation. Extend parity/inventory checks deliberately; keep unresolved coverage gaps visible rather than declaring L2/L3 from green script names.
4. **Dogfood the authoring loop without moving authority.** Index the accepted sources, distill revision-keyed rule/implementation/gate bridges, use impact+recall to propose maintenance work, and require owner review plus deterministic evidence before constitutional changes. Package this workflow for arbitrary repos only after it survives Engram's own drift cases.
