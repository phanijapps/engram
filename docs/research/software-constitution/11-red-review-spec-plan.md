## Findings
### BLOCKER
**1. Both templates violate the frontmatter parser before validation even starts.** spec.md:1–19; plan.md:1–6. What breaks: `factory.py` requires the file to start with `---\n`, but both start with an HTML comment. Failing scenario: ordinary factory rendering preserves the preamble, so `metadata()` rejects the generated artifact; `check_job_artifacts.py` also reports missing frontmatter. Fix: move each opening comment below its closing frontmatter delimiter—spec.md:34 and plan.md:20—so byte zero begins `---`.
Evidence: `.agents/skills/engram-factory/scripts/factory.py:75–78,140–152`; `tools/ci/check_job_artifacts.py:40–43`.

**2. Illustrative requirement IDs become phantom requirements.** spec.md:65–68. What breaks: the job checker collects every literal `REQ-nnn` occurrence, including delta examples, as a requirement. Failing scenario: retaining the instructions makes `REQ-003` and `REQ-014` require task coverage even though neither has a requirement definition. Fix: replace `(modifies REQ-014)` / `(removes REQ-003)` with `(modifies <existing requirement ID>)` / `(removes <existing requirement ID>)`, and require a source artifact revision or hash for cross-document targets.
Evidence: `tools/ci/check_job_artifacts.py:24–25,53–56,65–69`; in-memory extraction found four requirement IDs but only two requirement headings.

### DEFECT
**3. The worked pair teaches nonexistent traceability.** spec.md:76–77,125–133; plan.md:33–34,95–96,110–111. What breaks: the plan treats `REQ-002` as a preservation requirement although the spec defines it only as an unresolved question, and maps an undefined `AC-002`. Failing scenario: an agent copies the worked pair and produces coverage that looks complete while one behavior is undefined. Fix: replace the spec's `REQ-002` heading with a non-ID clarification placeholder; remove the preservation `REQ-002` references and the `AC-002` row from the plan example unless corresponding complete spec definitions are added.
The current job checker does not validate AC references; its silence would not establish correctness.

**4. Ready-state instructions omit mandatory metadata work.** spec.md:27–29,151–157; plan.md:14–18. What breaks: following the body instructions and changing status to ready still leaves an invalid timestamp and potentially missing direct-input references or snapshot provenance. Failing scenario: `datetime.fromisoformat("FILL: ISO-8601 with timezone")` fails; accepting a plan with required spec inputs also fails when `input_artifacts` remains empty. Fix: replace both `updated_at` values with `"{{timestamp}}"`; add a shared readiness instruction: “Before ready, populate the required source snapshot and direct-input `{path, sha256}` records, set ready status, and pass the applicable factory validation.”
Evidence: `factory.py:103–129,142–146`. `spec_ref` alone does not satisfy required direct inputs.

**5. Spec acceptance is written in three competing places.** spec.md:54–61,65–74,110–120. What breaks: journey Given/When/Then bullets, requirement WHEN/THEN bullets, and formal ACs independently restate behavior despite the instruction not to duplicate it. Failing scenario: an error response changes in the AC but remains stale in the journey or requirement bullets. Fix: replace spec.md:58–61 with “Acceptance: <AC IDs>”; replace lines 73–74 with “Acceptance: <happy-path AC ID>, <negative/boundary AC ID or justified exception>.”
A staff engineer would write the journey and normative requirement, then link acceptance—not perform the same behavior three times.

**6. Concrete fixture data contradicts the spec's own acceptance boundary.** spec.md:115–128. What breaks: the template prohibits concrete test instances in the spec, then prescribes `/nonexistent/gated/path` in its only AC example. Failing scenario: agents either copy fixture particulars into every AC or remove useful observable conditions to obey the prohibition. Fix: replace lines 115–120 with “ACs state observable conditions and outcomes; suite-only fixture construction and exhaustive permutations belong to tests”; replace the literal path in lines 126 and 128 with “a declared gated path absent on disk” and “that missing declared path.”

**7. Spec and plan both own the gate command and failure-impact narrative.** spec.md:93–97,131–136; plan.md:104–118. What breaks: duplicated commands and compatibility/failure statements can drift between approved behavior and executable structure. Failing scenario: the planner changes a test runner or mitigation, leaving a stale command or contradictory failure description in the spec. Fix: keep spec acceptance linked to a GATE ID and behavioral constraints; put executable gate commands only in the plan map. Replace plan.md:114–118 with “Reference the spec's interface and blast-radius constraints; describe only implementation dependencies, compatibility mechanisms, migration, rollout, and mitigation deltas.”
Behavior belongs in spec; structural enforcement belongs in plan. Referencing behavior is not the violation—maintaining a second authoritative copy is.

**8. The plan supplies runtime flow while claiming to supply component structure.** plan.md:57–70. What breaks: the advertised structure/responsibility concern is not answered by an exists/yes/no control-flow chart. Failing scenario: an M/L author copies this model and submits multiple runtime diagrams without showing component ownership or dependencies. Fix: replace lines 60–70 with “Show named components, responsibilities, and dependencies only when they clarify the seam; the sequence below shows runtime failure flow,” followed by a component graph linking the gate entry point, scanner, violation aggregator, and fixture.

**9. Required rollout reasoning is missing outside the toy example.** plan.md:87–102,113–118. What breaks: per-step revert cells do not require an author to explain partial deployment, persisted-state compatibility, or when rollback becomes unsafe. Failing scenario: a schema-changing implementation copies “revert the behavior commit” after irreversible writes. Fix: insert after line 102: “Deployment safety: state rollout order, mixed-version and persisted-state compatibility, rollback trigger/owner, and irreversible effects; give a reason when none apply.”
This belongs in implementation structure, not as another behavioral acceptance section.
