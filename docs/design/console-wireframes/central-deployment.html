Central deployment

One console watching several stores: the single-operator loopback model widened into a small fleet of registered engines, with the security model redesigned for it — not merely stretched.

future v1 is a local single-operator surface: loopback only, every request must originate from 127.0.0.1 / localhost / ::1, and anything else is refused with a named state. Central deployment changes that boundary — remote stores, network origins, and an authentication story that does not exist today. All of it is future.

Rationale — v1 today, what the future adds, why it is future open to explore

what exists in v1 — exactly the first row: one console, one engine, one local store, loopback-enforced. Requests from any other origin are refused with the origin-refused state — that refusal is the v1 security model working as designed.

what the future adds — a registry of engines with per-node health (the same named states as every other frame — a remote node can be store-locked or backend-unreachable exactly like the local one), aggregate inventory across stores, and per-node binding health.

why it is future — widening the origin boundary is a security decision, not a UI feature: authentication, transport, and per-node authorization all need designing first. The read-only posture survives — even a central console starts read-only against every store it watches.
